# Selectable install components: OS security baseline, improved Git, and a component checklist (v1)

The branch turns three previously-implicit capabilities into user-selectable install components. A new `install-os-security.sh` installs a general OS security baseline (ClamAV, UFW, AppArmor, fail2ban, unattended-upgrades, rkhunter, chkrootkit) that no longer depends on the Java web server path; a new `install-git-improved.sh` installs a modern Git plus git-lfs and companions with non-destructive system-wide defaults; and `galactic-cherry-installer` gains a `--checklist` component-selection step (with a numbered text fallback) plus `--desktop/--enable/--disable/--non-interactive/--help` CLI flags and `INSTALL_COMPONENTS`/`GC_COMPONENTS` env support. The manifest and the installer security slide were updated to match. The headline behavioral change is that the JWSTF/NitroWebExpress block, which used to run on every install, is now gated behind a component that defaults OFF.

Watch for: (confirmed) the `ubuntu-white` component only applies under the `gnome` desktop — selecting it with `mate`/`vanilla` silently no-ops with no log line. (confirmed) JWSTF now defaults OFF, a real behavior change from unconditional install; the security regression it could have caused is covered because ClamAV/UFW moved into the default-ON `security` component. (likely) `--desktop`/`--enable`/`--disable` read `$2` without checking it exists.

**Verdict**: NEEDS_CHANGES

## High-level view

The security baseline was extracted from `install-jwstf.sh` into a standalone, component-gated script. On the pre-change code the only path that actually installed ClamAV/UFW was the JWSTF installer, so a machine without the Java web server had no antivirus or firewall. Because the new `security` component defaults ON and JWSTF defaults OFF, a default install still lands the security baseline — the extraction is what keeps the JWSTF gating from becoming a security regression.

Component selection is driven by four parallel arrays (`COMPONENT_IDS`/`DESCS`/`DEFAULTS`) shared by the checklist step, the text fallback, and `--help`, so the selectable set stays in sync across surfaces. Selection flows through one predicate, `component_selected`, which every install block consults. All four repo components the user has worked on — ubuntu-white, security, git-improved, jwstf — are both surfaced as selectable and driven through to an install action, not merely declared.

The `ubuntu-white` component is the one place where "selectable" and "installed" don't line up: its overlay is wired only inside the `gnome` case of `step_install`, so a user who ticks ubuntu-white but installs MATE or vanilla gets nothing and no diagnostic. Every other component logs a NOTE when its installer is missing; this one doesn't log when the desktop is simply incompatible.

The Git script never sets `user.name`/`user.email` system-wide, writes `/etc/gitconfig` keys only when unset, and treats the PPA as best-effort with an archive fallback; the security script is similarly idempotent. Neither makes a silent privileged change, matching the repo's inspect→plan→apply→verify philosophy.

The CLI flags `--desktop`/`--enable`/`--disable` read `$2` and `shift 2` without checking the operand exists, so a value-less trailing flag misbehaves under `set -e` — low impact but worth a guard.

### Security baseline extracted from the JWSTF path

On the base branch, `install-jwstf.sh` was the only script that actually installed `clamav`/`clamav-daemon`/`ufw` and enabled freshclam — everywhere else the security tools were advertised (installer slide, welcome text, manifest) but never installed on a plain desktop. `install-os-security.sh` gives that baseline its own home: per-component `OS_SECURITY_*` toggles (default 1), root-guarded, `apt-get` presence checked, package list assembled only from enabled components, services enabled with `systemctl enable ... || true` so a missing unit never aborts the run. rkhunter/chkrootkit install whenever the script runs regardless of toggle — the header advertises this as the always-on rootkit-detector floor.

The UFW policy is deliberately scoped to the general case — `default deny incoming`, `default allow outgoing`, allow `OpenSSH` (falling back to `ssh`), `--force enable` — and explicitly does not open the JWSTF web ports (80/443/8080/8443/23), which `install-jwstf.sh` adds separately, so the two firewall configurations compose rather than fight when both components are selected. AppArmor is enabled only when `aa-enabled` reports it isn't already active, and `unattended-upgrades` is configured by rewriting `/etc/apt/apt.conf.d/20auto-upgrades` each run — both idempotent on re-run.

### Improved Git and the identity trust boundary

`install-git-improved.sh` installs `git git-lfs git-doc gitk git-gui`, runs `git lfs install --system`, and writes `/etc/gitconfig` defaults. The non-obvious design decision worth calling out: `set_default_if_unset` writes a key only when `git config --system --get` returns empty, so any value from the base image or a prior run is preserved, and `user.name`/`user.email` are deliberately never set system-wide — the one Git setting that must stay personal. The PPA is best-effort: `software-properties-common` is installed if `add-apt-repository` is missing, and any failure to add `ppa:git-core/ppa` falls through to the archive git without failing the run, the right posture for a restricted/offline install.

### Component selection wiring

Selection is normalized into a single space-separated `INSTALL_COMPONENTS` string consumed everywhere through `component_selected`. The env entry point accepts comma- or space-separated input; `components_enable`/`components_disable` de-duplicate and trim. The checklist step builds `tag description ON/OFF` triples and invokes the dialog frontend through a real argument array:

```
selection=$($DIALOG --title "Optional Components" \
    --checklist "..." $ROWS $COLS $LIST_ROWS "${args[@]}" 3>&1 1>&2 2>&3) || selection=""
INSTALL_COMPONENTS="${selection//\"/}"
```

Passing `"${args[@]}"` means component descriptions containing spaces and parentheses (e.g. "OS security suite (ClamAV, UFW, ...)") survive intact without word-splitting or re-quoting hazards — materially safer than the sibling `step_disk`, which still assembles a string and runs it through `eval $DIALOG ...`. In the text fallback, because component ids are single tokens with no spaces, the unquoted `for num in ${toggle//,/ }` toggle loop is safe.

All four components reach an install action: `ubuntu-white` → `install-gnome-desktop.sh` with `GNOME_THEME=ubuntu-white UBUNTU_WHITE_ICONS=1`, `security` → `install-os-security.sh`, `git-improved` → `install-git-improved.sh`, `jwstf` → `install-jwstf.sh`, each using the established "prefer file in target, else copy from host into `/tmp`, else log a NOTE" chroot pattern with a non-fatal `|| WARNING`.

### ubuntu-white only applied under GNOME

The overlay call sits inside `case "$INSTALL_DESKTOP" in ... gnome)`. If a user selects the `ubuntu-white` component but chooses `mate` or `vanilla`, the selection is silently discarded — no overlay, and unlike the missing-installer branches, no NOTE is written explaining why. The default flow hides this: the interactive desktop choice and the checklist are independent, and the defaults put both a desktop and ubuntu-white ON, so a MATE install with defaults will tick ubuntu-white and do nothing with it. Fix by applying the overlay where valid for MATE, or emitting a NOTE that the theme requires GNOME so the behavior is auditable in the log.

### JWSTF default-OFF

The JWSTF/NitroWebExpress block moved from unconditional execution to `if component_selected "jwstf"`, defaulting OFF. It is the single largest behavioral change in the branch: default installs no longer get the Java web server, nor the web-port firewall rules `install-jwstf.sh` would have added. This doesn't open a security hole because the antivirus/firewall baseline those installs used to inherit from the JWSTF script is now provided independently by the default-ON `security` component. Anyone relying on the old always-installed web server will see it disappear, so confirm "off by default" matches intent.

### argv parsing

`--desktop`/`--enable`/`--disable` consume `$2` and `shift 2` without checking that `$2` exists; a value-less trailing flag would misbehave. Low-severity robustness gap (documented usage always supplies a value), but an `[ -n "${2:-}" ]` guard with a clear error would harden it.

### Not tested

No runtime harness exists in this repo and none was added. `bash -n` passes for all three scripts and the manifest parses as JSON. Unverified by construction: the whiptail/dialog `--checklist` rendering and quote-stripping against a real frontend, the chroot install of each component against a live apt, and the UFW/AppArmor enable paths — none runnable in this sandbox.
