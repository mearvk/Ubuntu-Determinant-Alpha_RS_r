# White Edition Start button, popup alignment reworked via boxpointer _reposition wrap (v2)

The fix pass (f197357c74) reworks the popup-alignment mechanism that v1 flagged as a no-op and corrects the placement prose. Alignment no longer rides the menu `open-state-changed` signal; the extension now wraps the popup boxpointer instance's `_reposition`, calls the Shell original first, then shifts only the allocation-box X for center/right. Because the wrapper runs inside `_reposition` on every allocation, its X is the authoritative value and survives the relayout that clobbered the v1 approach. The invalid `setArrowOrigin(Clutter.Gravity.SOUTH_WEST)` call and its `Clutter` import are gone, `disable()` restores the wrapped `_reposition`, and every "bottom-left" claim in shipped prose is now "left of the panel."

Watch for: nothing blocking. Live popup anchoring, GSettings binding, and Adw/Gtk4 prefs rendering remain unexercisable in this sandbox with no running Shell, which is an accepted documented caveat rather than a defect (**confirmed**).

**Verdict**: APPROVED

## High-level view

The v1 alignment defect is genuinely fixed. The new override hooks the one point where popup geometry is authoritative, `BoxPointer._reposition` called from `vfunc_allocate` on every relayout, instead of the open signal that fires before the Shell positions anything. It is a monkey-patch of an instance method rather than a subclass, but it is scoped to one boxpointer instance, restored on disable, and defensible for an additive extension that cannot alter the Shell's menu construction.

The button-stays-left half is unchanged: `Main.panel.addToStatusArea(this.uuid, this._button, 0, 'left')` fixes the indicator at the front of the panel left box, and no alignment path touches it.

The placement prose is now honest across metadata, both gschema descriptions, the dconf default, prefs, and both READMEs, with the parent README explicitly stating the extension does not relocate the panel to the bottom. Schema, prefs, logos, and installer conventions from v1 still hold (uuid == dirname, settings-schema == gschema id, three alignment values and three logos with matching nick order, defaults-not-locks dconf, no em dashes in shipped prose).

### Alignment now runs inside the allocation cycle, not on the open signal

The v1 defect was structural: `_applyMenuAlignment()` fired on `open-state-changed` and set `actor.set_x` / `setArrowOrigin`, both discarded when the Shell positioned the boxpointer later on the same open. The vendored source confirms the ordering the fix relies on: `PopupMenu.open()` (js/ui/popupMenu.js:1115) calls `super.open()` (which emits `open-state-changed`) *before* `this._boxPointer.setPosition(this.sourceActor, this._arrowAlignment)` at line 1125, and final geometry is computed in `BoxPointer.vfunc_allocate` then `_reposition(box)` (js/ui/boxpointer.js:229-231, 480), ending in `allocationBox.set_origin(Math.floor(x), Math.floor(y))`.

The rework wraps the boxpointer instance's `_reposition`:

```js
this._origReposition = boxPointer._reposition;
boxPointer._reposition = function (allocationBox) {
    self._origReposition.call(this, allocationBox);
    self._applyHorizontalAlignment(this, allocationBox);
};
```

Running after the Shell original means origin, arrow side, and arrow origin are computed by the Shell first, and the override adjusts only X, re-applied on every relayout rather than set once and abandoned. `this.menu._boxPointer` is a real property created in the `PopupMenu` constructor (popupMenu.js:1012), so it is present when `_installAlignmentOverride()` runs during `_init`. This resolves v1 issue 1.

### Coordinate translation and clamp mirror the Shell's own reposition

`_applyHorizontalAlignment` computes `targetX` in stage space against `Main.layoutManager.getWorkAreaForMonitor(primaryIndex)`: center is `workArea.x + floor((workArea.width - menuWidth) / 2)`, right is `workArea.x + workArea.width - (padding + menuWidth)`, where `padding` is the `-arrow-rise` theme length and `menuWidth` is `get_preferred_size()` natWidth. The vendored `_reposition` (boxpointer.js:507-511) reads the same `padding = themeNode.get_length('-arrow-rise')` and clamps to `Math.min(resX, workarea.x + workarea.width - (padding + natWidth))`; the override's `minX`/`maxX` reproduce that range, so its clamp and the Shell's agree at the edges.

The stage-to-parent translation matches too. The Shell walks `parent.transform_stage_point(resX, resY)` up the parent chain until success (boxpointer.js:601-605); the override walks the identical chain from `boxPointer.get_parent()` for `targetX`. It then computes `dx = floor(px) - curX` and calls `allocationBox.set_origin(curX + dx, allocationBox.get_y())`, which reduces to `set_origin(floor(px), y)`: the Shell-computed Y is preserved and only X moves. The `curX` round-trip is redundant (both `curX` and `px` derive from the same transform) but harmless. Left returns early, leaving the Shell default untouched, which matches the "left opens near the button" contract. The `changed::start-menu-alignment` handler now only calls `boxPointer.queue_relayout()` when the menu is open, letting the wrapped `_reposition` re-apply with the new value.

### Arrow origin and Clutter import

The `actor.setArrowOrigin(Clutter.Gravity.SOUTH_WEST)` call (v1 issue 2, a Gravity enum where boxpointer.js:610 documents `origin` as a pixel coordinate) is removed, and the now-unused `Clutter` import is dropped. `grep` confirms zero `Clutter` references in the extension tree. The Shell's `_reposition` sets a correct integer arrow origin itself (boxpointer.js:600), and the override no longer touches it.

### Lifecycle restores the wrapped method

`destroyButton()` reassigns `this._alignedBoxPointer._reposition = this._origReposition` before nulling both references, so the instance patch does not outlive the extension even though the actor is about to be destroyed. It also disconnects both settings handlers, nulls `_settings`, and destroys the actor. `disable()` calls it and drops the button reference. No leak of the wrapper or dangling signal remains.

### Placement prose corrected to match behavior

Every shipped "bottom-left" claim is now "left of the panel" / "panel left box": metadata.json description, both gschema key `<description>`s, db/local.d/00-white-edition, extension.js comments, prefs.js group description, the extension README, and the parent conf/white-edition/README.md. The parent README additionally states the extension "does not itself relocate the panel to the bottom of the screen, which remains the separate Shell-layout concern noted above," which honestly represents the user's "remain in the left" requirement. The remaining "bottom-left" strings live only in `.agents/tasks/**` planning/history JSON (context.json, task.json, FEAT-*.json) and the v1 review file, which are internal artifacts, not user-facing prose. This resolves v1 issue 3.

### Runtime verification remains out of reach (accepted)

Static checks re-run and pass: `env -u NODE_OPTIONS node --check` on extension.js and prefs.js, `glib-compile-schemas --strict --dry-run` on schemas/, `xmllint --noout` on the three SVGs and the gschema, `bash -n install.sh`. `node --check` is syntax-only and does not resolve `resource:///` imports; live popup anchoring for each of the three values, GSettings binding, and Adw/Gtk4 prefs rendering can only be confirmed on a real Shell 46 session. This is v1 issue 4, documented in the extension README as a caveat and not a code defect. The `_reposition`-wrap design is argued correct against the vendored Shell 46 allocation cycle above, which is the strongest verification available in-sandbox.
