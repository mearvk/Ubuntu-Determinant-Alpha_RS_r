# White Edition Start button with configurable popup alignment (v1)

Adds an additive GNOME Shell extension (`white-edition@mearvk`) that plants a Start button in the panel's left box and opens a popup menu whose horizontal anchor is user-selectable (left/center/right) via a GSettings enum, with three bundled Ubuntu-themed SVG logos also selectable via GSettings. It ships a schema, an Adwaita/Gtk4 prefs UI, a palette-matched stylesheet, an ISO-target installer, a defaults-not-locks dconf entry, and documentation. The packaging, schema, prefs wiring, logos, installer, and conventions match the user's intent. The core alignment mechanism, however, does not work against the GNOME Shell 46 boxpointer it targets.

Watch for: the popup never actually moves to center/right (**confirmed**) - `_applyMenuAlignment()` fires on `open-state-changed` and sets `set_x`/`setArrowOrigin`, both of which the Shell's own `BoxPointer._reposition()` overwrites on the same open cycle. The button lands top-left, not "bottom-left" as claimed everywhere (**confirmed**), and `Clutter.Gravity.SOUTH_WEST` is not a valid argument to `setArrowOrigin` in Shell 46 (**confirmed**).

**Verdict**: NEEDS_CHANGES

## High-level view

The button placement satisfies the "stays on the left" half of the requirement: `addToStatusArea(uuid, button, 0, 'left')` inserts the indicator at the front of the panel's left box unconditionally, and nothing in the alignment path touches it.

The popup-alignment half is where the design breaks. The extension moves the popup by grabbing `this.menu._boxPointer`, computing a target X over the primary work area, and calling `actor.set_x(targetX)` plus `actor.setArrowOrigin(...)` from an `open-state-changed` handler. In Shell 46, `PopupMenu.open()` emits `open-state-changed` *first* and only *afterward* calls `_boxPointer.setPosition(sourceActor, arrowAlignment)`; the boxpointer then computes its final origin inside `vfunc_allocate` -> `_reposition()`, which sets `allocationBox` origin and `setArrowOrigin` from the source actor and arrow alignment alone. The extension's `set_x` and `setArrowOrigin` are clobbered on the same open, so the popup keeps anchoring under the button regardless of the setting.

The "bottom-left" language in the metadata, schema descriptions, READMEs, and dconf comment overstates what the diff delivers: the button is added to the panel's left box, which is top-left on a default GNOME panel. Nothing in this change moves the panel to the bottom.

The schema, prefs, logos, installer, and dconf entry are coherent and follow repo conventions (two enum keys with matching nick orders, uuid equal to the directory name, settings-schema equal to the gschema id, defaults-not-locks dconf, no em dashes in authored prose).

<details>
<summary>Issues (4)</summary>

1. **Popup alignment is a no-op** - `_applyMenuAlignment()` runs on `open-state-changed`, before the Shell positions the boxpointer, and its `set_x`/`setArrowOrigin` are overwritten by `BoxPointer._reposition()` during allocation. Center/right never take effect. Drive alignment through the supported lever (`_arrowAlignment` via `_boxPointer.setPosition(sourceActor, alignment)`, an offset source actor, or a `_reposition` override) and apply it during allocation, not on the open signal.
2. **`setArrowOrigin` given a Gravity enum** - `actor.setArrowOrigin(Clutter.Gravity.SOUTH_WEST)` passes a deprecated/absent-in-Shell-46 Gravity constant where an integer pixel coordinate is expected. Remove the call; `_reposition()` sets the arrow origin itself.
3. **"Bottom-left" is inaccurate** - the button is added to the panel left box (top-left on a default panel); no code moves the panel to the bottom. Either implement bottom placement or change the metadata/schema/README/dconf prose to "left of the panel."
4. **Runtime unverified in sandbox** - popup anchoring, live GSettings binding, and Adw/Gtk4 prefs rendering were only statically checked; the alignment bug would only surface on a live Shell. Confirm on a real Shell 46 session after fixing.

<summary>Details</summary>

### Popup alignment fights the boxpointer allocation cycle

The popup side is implemented in `_applyMenuAlignment()`:

```js
this._openStateId = this.menu.connect('open-state-changed', (_menu, isOpen) => {
    if (isOpen)
        this._applyMenuAlignment();
});
...
const boxPointer = this.menu._boxPointer;
...
actor.setArrowOrigin(Clutter.Gravity.SOUTH_WEST);
actor.set_x(targetX);
```

In the vendored Shell 46 source, `PopupMenu.open()` (js/ui/popupMenu.js) does:

```js
open(params = {}) {
    if (!super.open(params))   // emits 'open-state-changed', true  --> our handler runs HERE
        return false;
    ...
    this._boxPointer.setPosition(this.sourceActor, this._arrowAlignment);  // queues relayout
    this._boxPointer.open(animate);
```

The handler runs before `setPosition`, and the final geometry is computed later in `BoxPointer.vfunc_allocate` -> `_reposition(box)` (js/ui/boxpointer.js), which derives `resX` from the source actor extents and `_arrowAlignment`, calls `this.setArrowOrigin(arrowOrigin)` with its own value, and ends with `allocationBox.set_origin(Math.floor(x), Math.floor(y))`. Because position is applied through the allocation box (not the actor's `x` property) and recomputed on every relayout, `set_x(targetX)` has no lasting effect and the extension's `setArrowOrigin` is replaced. The setting reads and stores correctly and the prefs UI reflects it, but the popup does not move.

The supported way to shift a popup menu horizontally is to influence what `_reposition` consumes: `_arrowAlignment` (via `menu._boxPointer.setPosition(sourceActor, alignment)` with alignment in 0..1), a different/offset source actor, or a subclass that overrides `_reposition`. Whatever lever is chosen must be in place during allocation, not fired off the open signal and then abandoned.

### `Clutter.Gravity` is the wrong type and likely undefined

`setArrowOrigin(origin)` documents `origin` as a coordinate ("middle of the arrow, along the ... X axis"). `Clutter.Gravity.SOUTH_WEST` is a deprecated Clutter enum the Shell 46 codebase does not reference anywhere; under the GI in use it is most likely `undefined`, making the call `setArrowOrigin(undefined)`. Even resolved to its legacy integer (6) it would mean "arrow origin at 6px," not "anchor to the bottom-left." Drop the call; the arrow origin is the boxpointer's responsibility.

### "Bottom-left" overstates the placement

Metadata description, the schema key descriptions, both READMEs, and the dconf comment all say the button sits at the "bottom-left of the panel." The code only inserts into the panel's left box; on a stock GNOME panel that is the top-left. The parent `white-edition/README.md` notes bottom placement is a separate Shell-layer concern, and this diff does not implement it. Since the user's ask was "remain in the left" (satisfied) rather than specifically bottom, correct the prose to "left of the panel" unless bottom placement is actually wired up.

### Runtime behaviors remain unverified

The README documents that live popup anchoring, GSettings binding, and Adw/Gtk4 prefs rendering could not be exercised without a running Shell. The alignment defect is exactly the kind of issue that only manifests live, so once the mechanism is reworked it must be confirmed on a real Shell 46 session: button holds left, popup visibly moves for each of the three values, logo swaps live.
