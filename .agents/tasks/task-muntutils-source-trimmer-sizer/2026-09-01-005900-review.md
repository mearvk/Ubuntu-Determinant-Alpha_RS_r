# muntutils: reachability-based source trimmer and dual-audience size reporter

Adds `tools/muntutils/`, a native utility built in both C11 and C++17. A C core (`muntutils_fs.c`) walks a tree, measures logical byte sizes, and classifies files as source, artifact, or other; a C++ engine (`muntutils_trim.cpp`) scans source with a heuristic (non-compiler) parser, computes a conservative reachable set, and emits a slimmed copy with confidently-dead functions replaced by stub comments. `main.cpp` exposes `trim` and `report` subcommands. The tool is meant to be run and reviewed by hand (there is no runtime test harness in this repo, matching `size`/`limit`), so behavioral correctness rests on static review plus running the binary. It builds clean under `gcc/g++ 11.5.0 -std=c11/c++17 -Wall -Wextra -Werror -O2`, links the C object into the C++ binary, and runs correctly on sample trees.

Watch for: the conservative-reachability contract has a real hole (confirmed) — a live function whose only reference is a name in a string literal consumed by a *custom* (non-`dlsym`/`GetProcAddress`) loader is classified DEAD, and reported at 100% confidence because no unresolved construct fires. Under `--in-place` this rewrites the original into a stub. The safe-by-default gate, the mandatory `.bak` backup, and the dual-language and attribution requirements are all satisfied (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The safe-by-default contract is enforced where it counts: `run_trim` refuses to proceed when neither `--out` nor `--in-place` is given, the default path writes only into the separate output directory, and the in-place path writes a `.bak` copy and aborts the whole file rewrite if the backup cannot be created. Tested directly; all three hold.

Reachability is deliberately over-conservative in its structure: the reference scan is tree-wide rather than a precise per-caller graph, so any function named anywhere outside its own definition is kept, non-static functions are roots unless `--strict`, address-taken and `dlsym`/`GetProcAddress` string names are roots, and duplicate names are kept. The gap is upstream of it: `strip_noise` blanks all string literals before the reference scan, and the only string-borne references recovered are those adjacent to the literal tokens `dlsym`/`GetProcAddress`. Any other name-based dispatch (plugin registries, command tables, signal/slot names, config-driven dispatch) is invisible, so such a function is classified dead — and because that case trips no unresolved note, confidence is reported as maximal exactly when the classification is most likely wrong.

The report satisfies its contract: raw source stats, optional slim stats, compiled-artifact stats (`.so/.dll/.a/.o/.exe` plus magic-sniffed extensionless binaries), a plain-language summary for a non-specialist adult, and a programmer section. The known cosmetic case where stub comments make slim text larger than raw is clamped to 0.0 percent.

Dual-language is genuine, not vestigial: the C core's unmangled symbols (`mu_measure_tree`, `mu_enumerate_sources`, `mu_classify`) are linked into the binary and driven by both the trim engine and the reporter through the `extern "C"` API. The exact NCSU attribution string is present in all nine expected locations, framed as provenance not legal claim. Em dashes appear only in `.hss`/`.hsss`/`.mmd` headings and Makefile/README banner lines that match the existing `size`/`limit`/`pcopy` template convention, so they are consistent with the repo, not stray prose.

Build integration keeps `muntutils` dependency-free (`make -C tools muntutils` builds regardless of the pre-existing pcopy bug), but the aggregate `all` and `install` targets still route through pcopy and remain broken by that out-of-scope bug.

### Conservative reachability: the string-literal dispatch hole

The reference scan runs on `stripped` text, where `strip_noise` has blanked every string and character literal to spaces. The only way a name inside a string re-enters the root set is `collect_dynamic_symbols`, which walks the *raw* text but only for literal occurrences of `dlsym` and `GetProcAddress` and grabs the first quoted token after them. A project that dispatches by name through its own registry — `register("do_work")`, a command table keyed by string, GLib/Qt signal names, a Lua/Python binding table, a `getenv`-selected handler — presents none of those tokens, so the target function looks unreferenced and is classified dead. Reproduced with:

```c
static void live_via_custom_loader(void) { printf("real work\n"); }
static void my_register(const char *n);
int main(void) { my_register("live_via_custom_loader"); return 0; }
static void my_register(const char *n) { (void)n; }
```

`trim --out` reported `dead (removed): live_via_custom_loader` at `confidence: 100%` with no unresolved note. In `--out` mode only the slim copy is affected, but under `--in-place` the original is stubbed (after a `.bak`, so recoverable), which is exactly the correctness-critical path the design calls out. The conservative contract says a function is trimmed "only when provably unreferenced"; a name present in the source, just inside a string, is not proven unreferenced. The fix that fits the existing shape is to have `collect_dynamic_symbols` (or a sibling pass) collect *all* quoted identifiers whose text equals a known function name and add them as roots, independent of `dlsym`/`GetProcAddress`.

### Confidence is highest exactly where the analysis is blindest

`result.confidence = penalty >= 0.6 ? 0.4 : (1.0 - penalty)` with `penalty = 0.03 * unresolved.size()`. Unresolved notes fire for preprocessor conditionals and for the `(*` + `)(` function-pointer heuristic. The string-dispatch case above trips neither, so confidence stays at 1.0 while a live function is being removed. Confidence should be capped below 100% whenever the tool both proposes a removal and observes string literals in the tree that match defined function names, so the reported number degrades in the situation that actually endangers correctness rather than only for the constructs it happens to pattern-match.

### Safe-by-default: failure modes verified

`run_trim` refuses with an error when `!in_place && out_dir.empty()` — verified `trim src` with no `--out` exits non-zero and writes nothing. In-place writes `<file>.bak` first and, if the backup write fails, aborts before rewriting the original; if the slim write fails the error preserves the backup path. Confirmed both `.bak` files are created and contain the pre-trim text while the originals become stubbed. Only files that actually change are backed up (`if (slim == ft.raw) continue`), so a clean file is neither backed up nor rewritten — meaning a failed backup can only block a file that was going to change anyway.

### The stub-growth clamp

The shrink percentage guards `slim_src <= raw_src` before computing, so the recorded case where a stub comment makes a tiny dead function's slim text larger than raw yields 0.0 percent rather than a negative number — reproduced (slim 624 B vs raw 530 B reported as "about 0.0 percent smaller"). The summary separates source-text reduction from compiled-program size, which matters for a non-specialist reading raw-vs-slim numbers.

### Output directory is not excluded from the walk

Enumeration happens before any writing, so a single run is unaffected, but the walk does not exclude `out_dir`. With `--out src/slim_inside`, a first run scanned 1 file and a second run scanned 2 (picking up the generated slim copy). The generated files are still source-category and get re-analyzed and re-copied, conflating output with input across repeated runs. Rejecting an `--out` that resolves inside `<src-tree>`, or skipping it during enumeration, closes this.
